# Zone-Parametric Core and NL Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make core, training, CI and the integration zone-parametric and ship NL as the second
bidding zone (own model, bundled), plus a map of the supported zones on the project site.

**Architecture:** One global weather-point catalogue (every point has one variable set, so raw
files and Open-Meteo requests are shared across zones). DE-LU keeps its feature layout
unchanged (`layout="de_lu"`); NL uses the generic layout of the research builder
(`research/zones/genfeat.py: feature_names/_weather_features`, without the `hydro`, `de_extra`
and `de_price` options). Both get schema-2 `rel` + wall-clock lags from `core/features.py`.
Training and CI loop over `ZONES`; the integration already keys everything by zone slug.

**Tech Stack:** numpy (core), scikit-learn 1.9.1 (training), Home Assistant tests, Jinja site
builder, Natural Earth geodata (public domain) for the map.

**Spec:** user request 2026-10-23 ("NL als erste neue Zone", "eine Karte auf der Webseite, die
die unterstützten Zonen anzeigt"); research: `research/zones/` (`zonecfg.py` NL entry,
`genfeat.py`, `bt.py` variant `rel`: NL MAE 2.20 ct, skill 0.37, bias −0.56, monthly refit,
600 iterations, eval 2025-10..2026-10). Base branch: `schema-2` (feature schema 2).

## Global Constraints

- `core/` stays numpy-only; minimum Home Assistant 2024.11.
- **DE-LU must not change:** its `feature_names`, feature values, Open-Meteo request
  parameters, model file and `tests/fixtures/golden_features.json.gz` stay byte-identical.
  `FEATURE_SCHEMA` stays 2 (NL is new, nothing old changes meaning).
- NL prices: Energy-Charts `license_info` = "CC BY 4.0 (creativecommons.org/licenses/by/4.0)
  from Bundesnetzagentur | SMARD.de" (checked 2026-10-23). Only CC BY data goes into the
  public raw archive.
- Energy-Charts rate limits: price requests stay serial with the existing pauses.
- Commit per task in the repo's message style with the session attribution lines; no push.

## Decisions

- **Point catalogue (`core/zones.py`):** `POINTS: dict[str, tuple[Point, tuple[str, ...]]]`,
  the 22 DE-LU points with their current variable sets plus the five NL points from
  `zonecfg.NEW_POINTS` (`nl_borssele, nl_flevoland, nl_groningen, nl_randstad, nl_brabant`,
  vars `S_VARS = wind_speed_100m, temperature_2m, cloud_cover`). A test asserts each point has
  exactly one var set and DE-LU's points/vars equal today's.
- **Zone fields:** add `name` (English label, e.g. "Netherlands"), `country` (calendar key),
  `layout` (`"de_lu"` | `"generic"`), `default_vat`, and the generic roles `own, nb, wind,
  solar, hydro, nb_wind, nb_hydro` (tuples of point names, NL values verbatim from
  `zonecfg.ZONES["NL"]`). Keep DE-LU's existing fields working (or derive them) so its feature
  code is untouched. `Zone.point_sets() -> list[tuple[dict[str, Point], tuple[str, ...]]]`
  groups own+nb points by var set in first-appearance order; for DE-LU it must equal today's
  `[(points, weather_vars), (neighbor_points, neighbor_vars)]` exactly (sources and training
  fetch use it).
- **Features:** `feature_names(zone) -> tuple[str, ...]`; `FEATURE_NAMES` stays as the DE-LU
  tuple for existing callers that are DE-only (golden test), every zone-dependent caller
  (`forecast.py`, `model.py` checks, `training/*`, tests' random models) uses
  `feature_names(zone)` / the model's zone. Generic layout = `genfeat.feature_names(cfg)` with
  `hydro_extra=False, de_extra=False`, no `de_price`, no capacity columns; values =
  `genfeat._weather_features` (same arithmetic order). `holiday`/`offday` from the calendar.
  The model file's `features` list is checked against `feature_names(ZONES-by-slug[model.zone])`.
- **NL holidays (`core/calendar.py`):** `holidays(country: str, year: int) -> frozenset[date]`,
  `"DE"` = today's `de_holidays`, `"NL"` hand-coded: Nieuwjaarsdag, Goede vrijdag, Eerste and
  Tweede paasdag, Koningsdag (27 Apr, 26 Apr when the 27th is a Sunday), Bevrijdingsdag (5 May
  only when `year % 5 == 0`), Hemelvaartsdag, Eerste and Tweede pinksterdag, 25 and 26 Dec.
  Test: equals `holidays.country_holidays("NL", years=y)` for 2020–2040 (`holidays` as a
  pinned test-only requirement, the package version research used: 0.107).
- **Raw data layout:** shared: `prices/<zone code>/*.json`, `weather/<point>_<YYYY-MM>.json`
  (one file set per point, whatever zones use it), `installed_power.json` (DE only).
  `training.fetch --zones DE-LU,NL` (default: all of `ZONES`) fetches the union of points once.
  For the local NL training, seed the raw dir from `research/data/raw` (it already holds
  `prices/NL` and all 22 DE-LU points, 2024-03 … 2026-10) plus
  `research/data/zones/weather/nl_*_YYYY-MM.json` (same file format, 32 months each), then
  run the fetch to fill gaps.
- **Training:** `--zone CODE` on `training.train`, `training.ci`, `training.fetch`
  (`ZONE` constant goes; the workflow asks `python -m training.zones` or similar for the list).
  Capacity only where the zone has it (DE-LU); NL has `capacity={}` in its model file.
  Bundled NL model: cutoff 2026-10-01 → version `nl-2026-10`, files `nl.json.gz`,
  `nl.backfill.json.gz` in `custom_components/spot_forecast/models/` (and in
  `tests_ha/fixtures/model/` if the HA tests need it). Report the NL walk-forward metrics.
- **CI (`train.yml`):** one `train` job loops over the zones serially; per zone: download the
  zone's previous models (today's jq block, parametrised), `training.ci --zone`, outputs to
  `out/<slug>/`. Manifests chain: zone N gets as `--previous-manifest` the manifest written by
  the last zone that passed, else the downloaded one; the final manifest is the last one
  written. A failing or data-lagged zone never blocks another. `publish` uploads each passed
  zone's versioned files, then the final manifest once, opens one issue per failed zone (title
  per version, as today). Timeout sized for two zones. `accept_incomparable` applies to all
  zones (a zone with no manifest entry passes on skill alone, as today). `train` outputs the
  list of passed versions (not one `version` string); `publish` derives each zone from it.
  Pin in tests (`tests/test_workflows.py` and/or `training.ci` tests on chained manifests):
  (a) only NL passes → DE-LU keeps its previous entry, the manifest is uploaded once;
  (b) no zone passes → no manifest upload at all; (c) one zone `already_published`, the
  other passes → the passing zone's entry lands, the other entry is untouched.
- **Release/validate tools:** `tools/fetch_published_model.py` and `tools/check_model_age.py`
  handle every zone (loop), keeping today's per-zone behaviour (schema mismatch keeps the
  committed model, exit 0).
- **Integration:** config flow zone selector shows `"{code} – {name}"` (translated names via
  translations `selector` options, en + de); VAT option default from `zone.default_vat`
  (DE-LU 19, NL 21) for new entries, existing entries keep their stored value. The default
  must be zone-aware at every read: `coordinator.vat` falls back to `zone.default_vat`, not
  `const.DEFAULT_VAT` (drop that constant). HA test: fresh NL entry with no options → the
  total price uses 21 %. Sources use
  `zone.point_sets()` (NL: three Open-Meteo requests per run). Everything else is already
  zone-keyed. Known DE-LU hard-wiring outside tests: `tools/build_site.py` (`MODEL`,
  `BACKTEST`), `tools/site_data.py` (default zone), `tools/card_scenarios.py` (screenshots,
  may stay DE-LU), `core/features.py` (`FEATURE_NAMES` from `DE_LU`), `const.DEFAULT_VAT`.
  The HA tests are DE-LU by design; add NL ones, don't rewrite those.
- **Site map:** `tools/zone_map.py` (run by hand, output committed) builds
  `site/data/zone_map.json` from Natural Earth 1:10m admin-0 and admin-1 (public domain, pinned
  release of `nvkelso/natural-earth-vector`: tag v5.1.2, `geojson/ne_10m_admin_0_countries.geojson` and
  `geojson/ne_10m_admin_1_states_provinces.geojson`; select regions by `iso_3166_2`, not by
  name — v5.1.2 spells Sjælland "Sjaælland" and has the pre-2020 Norwegian counties): context countries of northern/central Europe in
  grey, and shapes for DE-LU (DE+LU), NL (European part only: NE's Netherlands is a
  multipolygon with the Caribbean municipalities, so clip to a Europe bbox before
  projecting), DK1 (DK-81, DK-82, DK-83), DK2 (DK-84,
  DK-85), NO2 (approximation: NO-08 Telemark, NO-09 Aust-Agder, NO-10 Vest-Agder, NO-11 Rogaland — say "approximate" in the data; county names
  differ between NE releases (pre/post 2020 merger), so read them from the pinned file and
  fail loudly on a missing name). Downloads go into their own empty directory and are parsed
  with `python -I`. Projected
  (e.g. Lambert azimuthal equal-area around 10°E 55°N), simplified, SVG path strings, a few
  tens of KB. `tools/build_site.py` renders an inline SVG section: zones with a bundled model
  are highlighted (data-driven, so phases 3/4 only add a model), others not drawn as zones;
  hover/tap title and a small list with zone name and MAE D+1…D+6 from each bundled model's
  `metrics`. No external JS. Colours as CSS tokens with dark mode like the rest of the page;
  works at phone width. i18n keys in `site/i18n/en.json` and `de.json`; credit "Natural Earth"
  in the sources section. `tests/test_site.py`: one highlighted path per bundled model.

## Review Focus

- DE-LU unchanged: golden fixture, DE-LU model sample check and the HA DE-LU tests pass
  without touching their fixtures; DE-LU Open-Meteo request params identical (test).
- Two entries at once (DE-LU and NL): separate stores, statistics ids, model downloads and
  manifest entries; a model update for NL never touches DE-LU files (HA test).
- NL calendar edge cases: 2025 Koningsdag Saturday 26 Apr, Bevrijdingsdag only in lustrum
  years (2025, 2030), Easter-based days across 2020–2040 (pure test against `holidays`).
- A model file whose zone is NL but whose `features` are DE-LU's (or the reverse) is rejected
  with `ModelMismatch`, not mis-applied (pure test).
- CI: NL gate fails → DE-LU still publishes and the manifest keeps NL's previous entry (or
  none); the reverse too (workflow test or `training.ci` test on chained manifests).
