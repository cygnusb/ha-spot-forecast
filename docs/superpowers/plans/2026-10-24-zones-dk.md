# DK1 and DK2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship DK1 and DK2. Each zone's forecast is the 50/50 blend of its own model (generic
layout plus DE-LU inputs) and the DE-LU model's forecast, with the DE-LU model embedded in the
DK model file.

**Architecture:**
- **Zone inputs:** a zone can declare input zones whose prices it reads (`price_inputs`) and
  extra raw weather points (`raw_extra`). DK1 and DK2 read DE-LU prices and the ten DE-LU
  points.
- **Composite model:** a zone can have a `parent` zone (DE-LU). Its model file then carries
  the parent's complete model document, and the forecast blends the two slot by slot.
- **Training:** DE-LU is trained first. The DK training gets the DE-LU candidate model and its
  walk-forward predictions, so the walk-forward report, backfill and gate are all on the blend.

**Tech Stack:** numpy (core), scikit-learn 1.9.1 (training), Home Assistant tests.

**Spec:**
- Research: `research/zones/README.md`, section "DK1 and DK2".
- Variant `desetprel`: `research/zones/bt.py` (`dataset`, `relative`, `DE_REL`) and
  `research/zones/genfeat.py` (`feature_names`/`build_features` with `cfg.extra = {"raw_extra":
  DE-LU points not already in the zone, "de_price": True}`).
- Results, production setting, ct/kWh:
  - DK1: blend 2.18 (own model 2.34, DE-LU reused 2.29).
  - DK2: blend 2.35 (own model 2.48, DE-LU reused 2.45).
- Base branch: `zones-nl` (PR #3), which stacks on `schema-2` (PR #2).

## Decisions

### Zones (`core/zones.py`)

- **Points:**
  - DK1 and DK2 roles verbatim from `research/zones/zonecfg.py`.
  - New catalogue points from `NEW_POINTS`:
    - DK1: `dk1_horns_rev, dk1_north_jutland, dk1_aarhus, dk1_south_jutland`
    - DK2: `dk2_copenhagen, dk2_kriegers_flak, dk2_lolland, dk2_bornholm`
    - shared: `no2_sirdal, se3_gothenburg, se4_malmo`
  - Each new point keeps its research variable set (`S_VARS` / `N_VARS`).
- **Other fields:**
  - `tz` Europe/Copenhagen, `country` "DK", `default_vat` 25.0.
  - `name`: "Denmark West" / "Denmark East".
- **New zone fields:**
  - `raw_extra`: the DE-LU points not already among the zone's own points, in DE-LU order.
  - `price_inputs = ("DE-LU",)`.
  - `parent = "DE-LU"`, `blend = 0.5`.
- **`point_sets()`:** must also cover `raw_extra` and, when there is a parent, all of the
  parent's points. A DK run needs all 22 DE-LU points (the DE-LU feature matrix uses bayern,
  `nb_alps_*`, `nb_fr_*`, `nb_fi`, …). A test pins the exact groups for DK1 and DK2. The
  DE-LU and NL groups do not change.

### DK holidays (`core/calendar.py`)

- Same days as research `offdays("DK", y)`: `holidays.country_holidays("DK")` plus 24 Dec and
  31 Dec.
- `holidays` 0.107 DK includes Store Bededag only up to 2023 and Easter Sunday/Whit Sunday.
  Hand-code exactly what the package gives for 2020–2040, plus the two eves.
- Test against the package plus the eves.

### Features (`core/features.py`)

- **Names:** the generic layout with `raw_extra` raw columns after the own points' raw
  columns, then `DE_PRICE` at the end. This is research `feature_names(cfg)` with
  `cfg.extra = {"raw_extra": ..., "de_price": True}`.
- **DE price features:**
  - Computed from the DE-LU price series and DE-LU daily stats (Europe/Berlin).
  - `de_p_lastday` / `de_p_lastweek` use the schema-2 wall-clock lag: same local hour, known
    only up to the anchor day's end. Research used UTC lags; use wall-clock like every other
    lag (DK and DE share their UTC offset).
  - All six are relative: `(x − own D_mean7) / own scale` (`DE_REL` in `bt.py`).
- **Interface:** `build_features(..., extra_prices: Mapping[str, tuple[Hourly, DailyStats]] |
  None = None)`. A zone with `price_inputs` and no matching entry raises
  `InsufficientHistory`.
- **Parity test** against research `genfeat` plus `relative`, on a slice of the real data.
  Skip it without `research/data`. Compare the lag columns only on anchors away from DST
  switches.

### Composite model (`core/model.py`, `core/forecast.py`)

- **File format:**
  - The model document gets an optional `"parent"`: the parent zone's complete model
    document (same format, feature schema and checks, its own `zone`), and `"blend"`, the
    weight of the zone's own model (0.5).
  - `load_model` checks the following and raises `ModelMismatch` otherwise:
    - `parent` is present exactly when the zone has `parent` in `ZONES`;
    - the parent's zone is that parent;
    - the parent's `feature_schema` equals the code's.
  - The parent's trees go through the same `_check_trees`. The node cap applies per tree set,
    as today.
- **Fields:** `ModelFile.parent: ModelFile | None`, `ModelFile.blend: float`.
- **`sample_check`:** checks the parent too.
- **`run_forecast`:**
  - Takes `extra_prices` and `extra_weather` (the parent's inputs come from the same weather
    mapping, since `point_sets` already includes them).
  - When `model.parent` is set, it also runs the parent on its own zone: DE-LU prices, DE-LU
    daily stats, `parent.capacity`.
  - Each slot's median, `p90_raw` and `p10_raw` are `blend·own + (1−blend)·parent`, matched
    by `(time, h)`. `valid` requires both sides to be valid.
  - The conformal offsets in the DK model file are for the blended quantiles (training
    computes them on the blend).

### Training

- **`training/dataset.py`:**
  - A zone with `price_inputs` loads those prices too.
  - A zone with a parent gets `X_parent`, the parent zone's feature rows aligned with the
    zone's rows by `(anchor, time)`. Rows without a parent row are dropped, and the drop count
    is logged. The gate and `previous_model_predictions` can then evaluate any composite
    model.
- **`training/train.py`:**
  - For a zone with a parent: `--parent-model FILE` (the DE-LU candidate of the same run) and
    `--parent-predictions FILE`, which DE-LU's training writes next to its model as
    walk-forward predictions keyed by `(time, h)`.
  - DE-LU training always writes that predictions file.
  - **Walk-forward on the blend:** in each refit month, own-model predictions are blended with
    DE-LU's walk-forward predictions for the same rows. DE-LU's predictions come from a model
    with the same monthly cutoff, so both halves stay out of sample.
  - Conformal offsets, metrics, the backfill and the report are on the blend.
  - The written DK model embeds the DE-LU candidate (`dump` of `--parent-model`).
- **`training/ci_zones.py`:**
  - Order DE-LU, NL, DK1, DK2.
  - The DK zones get DE-LU's candidate and predictions from `out/de_lu/`.
  - If the DE-LU training itself errors, DK1/DK2 are skipped that month and each logged as an
    error. Their published models stay.
  - If DE-LU only fails its gate, DK still trains with the DE-LU candidate, which is what a DK
    install would blend with. Document this.
  - Tests pin both cases.
- **Gate:** `previous_model_predictions` handles composite previous models via `X_parent`. The
  gate compares blend with blend.
- **Bundled models:**
  - Cutoff 2026-10-01; versions `dk1-2026-10` and `dk2-2026-10`.
  - Train them the way the DE-LU bundled model was trained (`--walk-forward-from 2025-04-01`).
  - The parent is the bundled `de_lu-2026-10`, and its walk-forward predictions come from
    retraining DE-LU the same way. Check that the retrained DE-LU model file is byte-identical
    to the committed one; if it is not, use the committed file as parent and say so.
  - Raw data:
    - `research/data/raw` (DE-LU points, `prices/DK1`, `prices/DK2` if present there, else
      `research/data/zones/prices/DK1|DK2`);
    - `research/data/zones/weather/` for the new points.
    - Seed a raw dir under the scratchpad.
- **Acceptance**, walk-forward over all horizons on the comparable window (issue days from
  2025-10-01):
  - DK1 blend MAE ≤ 2.28 and DK2 blend MAE ≤ 2.45, i.e. at least as good as reusing the DE-LU
    forecast.
  - P90 exceedance 9–15 %.
  - Otherwise STOP and report per-horizon numbers for own, parent and blend.

### Integration

- **Coordinator and backfill:**
  - Fetch the zone's prices plus each `price_inputs` zone's prices (Energy-Charts, serial).
  - Pass them to `run_forecast`.
  - The previous-runs backfill fetches all point groups of `point_sets()`.
  - Diagnostics show the parent's version.
- **Config flow:** DK1 and DK2 are listed with their names; VAT default 25 %.
- **Model update:** a DK model download is a single file; nothing changes there. The manifest
  entry is per zone, as today.
- **HA tests:**
  - Recorded DK1 fixtures: DK1 and DE-LU Energy-Charts responses, Open-Meteo forecast and
    previous runs for the DK1 groups.
  - DK2 may reuse them with a test that it sets up.
  - A DK1 entry sets up, forecasts, has `sensor.spot_forecast_dk1_*` entities and VAT 25 %.
  - A failed DE-LU price request keeps the last forecast, as any source error does.
- **Size:** the integration zip grows by two composite models (≈ 3.5 MB each). Note the total
  in the report.

## Review Focus

- A DK model whose embedded parent is missing, for the wrong zone, or of another schema →
  `ModelMismatch`, not a forecast from half a model (pure tests).
- The DE-LU price request fails or comes back short for a DK entry → no forecast from NaN DE
  features is presented as valid. Same handling as a failed own-price request (HA test).
- DST: on 2026-10-25 and 2027-03-28 the DE price lags of a DK row equal those of the DE-LU row
  at the same UTC hour (pure test).
- A DK entry next to a DE-LU entry: independent models, so a DE-LU model update does not
  change the DK forecast's parent (HA test).
- CI: DE-LU errors → DK skipped and their manifest entries kept. DE-LU gate fails → DK still
  published if its own blended gate passes (tests in `tests/training/test_ci_zones.py`).
